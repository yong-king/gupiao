# 28 高提醒企业微信/微信投递规范

## 1. 背景

当前项目已经具备提醒中心、提醒事件、通知记录和前端提醒页，但高风险提醒仍然只停留在系统内部页面中。对于真正需要用户立即注意的高等级提醒，仅靠用户主动打开 PC 端页面查看并不够。

因此需要新增“高提醒外部投递”能力，把提醒中心中的高等级提醒自动发送到企业微信，或者在可行条件下通过微信相关能力送达用户。由于不同消息通道的接入方式存在差异，系统需要引入统一的通道抽象，并为 MCP 接入留出明确边界。

本模块聚焦 PC 端后台和控制台场景，不负责移动端推送。

## 2. 目标

- 将提醒中心中的高等级提醒自动投递到外部消息通道。
- 第一优先支持企业微信（WeCom）机器人或应用消息能力。
- 为微信类通道预留抽象与配置，但不承诺第一阶段全部打通个人微信。
- 支持通过 MCP 或等效通道适配层接入外部消息能力。
- 在 PC 控制台中可见配置状态、测试结果、最近投递结果和失败原因。
- 保持现有提醒中心作为系统内主记录来源。

## 3. 非目标

- 不实现自动买卖或自动下单通知。
- 不实现个人微信绕过官方限制的非合规接入。
- 不实现群发营销消息。
- 不在本阶段接入短信、邮件、电话等多渠道通知。
- 不要求移动端推送在本规范中完成。

## 4. 通道策略

### 4.1 第一阶段通道优先级

第一阶段通道策略：

1. 企业微信机器人 Webhook
2. 企业微信应用消息（如已有企业内部应用配置）
3. 微信相关能力预留抽象，不承诺立即实现

### 4.2 微信能力边界

必须在规范中明确：

- 个人微信没有稳定、通用、官方支持的服务器直发能力可直接替代企业微信；
- 如果用户要求“发到微信”，第一阶段可以理解为：
  - 企业微信；
  - 或者通过后续 MCP/第三方合规桥接能力接入的微信通道；
- 不得使用不透明、不可审计、违反平台规则的个人号自动化方案。

## 5. 功能范围

### 5.1 必须实现

#### 5.1.1 高提醒筛选

- 仅当提醒等级为 `high` 或 `critical` 时触发外部投递；
- 中低等级提醒继续只保留在系统内提醒中心；
- 同一条提醒在冷却窗口内不得重复外发。

#### 5.1.2 通道抽象

系统需要有统一的消息投递抽象，例如：

- `alert_delivery_channel`
- `alert_delivery_message`
- `alert_delivery_result`

至少支持以下状态：

- `pending`
- `sent`
- `failed`
- `suppressed`

#### 5.1.3 企业微信通道

第一阶段必须支持企业微信机器人或企业微信应用消息二选一落地，推荐优先机器人 Webhook。

消息内容至少包含：

- 风险等级；
- 股票代码；
- 市场；
- 信号类型；
- 提醒摘要；
- 触发时间；
- 当前系统链接或详情提示；
- 风险提示边界说明。

#### 5.1.4 MCP 接入边界

如果外部消息能力通过 MCP 接入，必须满足：

- MCP 仅负责执行外部发送动作；
- 项目内部仍需保留发送前筛选、内容组装、去重、冷却和发送结果记录；
- MCP 不得绕过项目自己的审计日志；
- MCP 失败时必须回写失败结果和错误摘要。

#### 5.1.5 PC 端控制台能力

PC 端至少新增或扩展以下能力：

- 外部提醒投递配置区域；
- 显示当前启用通道；
- 显示 Webhook 或通道配置是否已就绪；
- 提供“发送测试消息”按钮；
- 提供最近投递记录列表；
- 在提醒详情或日志中能看到是否已外发。

#### 5.1.6 审计与日志

每次高提醒投递必须记录：

- alert_event_id
- channel_type
- channel_target
- request_summary
- response_summary
- status
- error_message
- created_at

### 5.2 应该实现

- 支持多通道优先级配置；
- 支持启用/禁用某个通道；
- 支持测试消息不进入真实提醒统计；
- 支持前端显示最后一次投递时间与结果。

### 5.3 范围外

- 多租户复杂通道路由；
- 消息模板可视化编辑器；
- 人工审核后再发送；
- 移动端推送；
- 复杂消息编排。

## 6. 用户场景

### 6.1 正常场景

- 用户在 PC 端配置企业微信机器人 Webhook；
- 某只股票触发 `high` 风险提醒；
- 系统将该提醒写入内部提醒中心；
- 后端判断满足外发条件；
- 系统调用企业微信通道或 MCP 通道发送消息；
- 前端可查看发送成功记录。

### 6.2 失败场景

- 企业微信 Webhook 配置缺失；
- MCP 服务不可用；
- 第三方接口返回失败；
- 命中冷却窗口而被抑制；
- 消息内容非法或过长。

失败时必须：

- 不影响系统内提醒中心展示；
- 记录失败结果；
- 在控制台中可看到失败原因。

## 7. 后端设计

### 7.1 推荐新增模块

- `backend/internal/delivery/`
- `backend/internal/wecom/` 或 `backend/internal/notifychannel/`

### 7.2 推荐新增数据结构

可新增表或持久化结构：

- `alert_delivery_channels`
- `alert_delivery_logs`

如果第一阶段先以内存或现有日志持久化过渡，也必须保证后续可迁移。

### 7.3 发送触发时机

推荐触发时机：

- 在 `alert_event` 创建并写入后，异步触发外部投递；
- 或在刷新完成后统一处理新增高提醒。

无论哪种方式，都必须保证：

- 内部提醒创建成功优先；
- 外部投递失败不回滚内部提醒；
- 同一提醒不会在冷却窗口内重复外发。

## 8. 配置要求

### 8.1 后端配置

后端配置需要支持：

- 是否启用外部高提醒投递；
- 默认通道类型；
- 企业微信 Webhook 或应用配置；
- MCP 服务启用开关；
- 冷却时间；
- 测试目标名称。

### 8.2 敏感信息要求

以下信息不得写死进代码仓库：

- 企业微信 Webhook；
- 企业应用密钥；
- 微信桥接凭证；
- MCP 远端敏感凭证。

必须通过环境变量或本地私有配置注入。

## 9. 前端 PC 控制台要求

### 9.1 页面位置

可放在：

- 设置页中的“外部提醒通道”区域；
- 或单独的“提醒投递”管理区域。

### 9.2 页面必须展示

- 通道名称；
- 启用状态；
- 配置状态；
- 最近一次测试发送结果；
- 最近若干条高提醒投递记录。

### 9.3 页面交互

- 保存通道配置；
- 发送测试消息；
- 刷新投递日志；
- 查看失败原因。

## 10. MCP 设计要求

如果使用 MCP，需满足以下约束：

- MCP 工具命名和用途清晰，例如 `send_wecom_message`；
- 项目内部封装统一调用入口，不在业务代码里散落调用；
- 对外部返回结果做结构化转换；
- 失败时记录到 `operation_logs` 和投递日志中；
- MCP 仅作为通道执行器，不替代业务判断层。

## 11. 测试要求

### 11.1 必须测试

- 高提醒筛选逻辑；
- 冷却去重逻辑；
- 通道配置校验；
- 企业微信发送适配层；
- MCP 通道失败回写；
- 前端配置页和投递记录展示。

### 11.2 建议测试

- 测试消息发送；
- 第三方接口超时；
- 重试策略；
- 长文本截断。

## 12. 验收标准

- 高等级提醒可以触发外部投递。
- 企业微信作为第一阶段主要通道可配置、可测试、可查看结果。
- 微信能力边界在文档中有明确说明，不走不合规方案。
- PC 控制台可查看外部投递配置和结果。
- 如果接入 MCP，调用链路可审计、可失败回写。
- 不影响原有提醒中心和内部通知记录。
